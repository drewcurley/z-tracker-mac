# T-019 — Bugfix: overworld tile icons used a dead ZHelper asset

## Description
User-reported: *"why are you using icons from zhelper instead of from the
z-tracker? also you have those icons mapped completely wrong."* Confirmed by
reading the reference source, not just visual comparison:
`s_icon_overworld_strip39.png` — bundled since `T-007` and the basis of the
entire tile-icon rendering system — is loaded in the reference app's own
code into a variable literally named `zhMapIcons`
(`Z1R_WPF/Graphics.fs:767`), and a repo-wide search confirms that variable
is never referenced anywhere else in either the WPF or Avalonia targets.
It's dead code: a leftover from the ZHelper tool that inspired Z-Tracker,
before its overworld tiles were redesigned with smaller icons
(`Zelda1RandoTools/doc/about.md`: *"Overworld tiles in particular required
redesigning new, slimmer icons, rather than the full-tile icons I had
copied from ZHelper"*).

The real system, confirmed by reading `theInteriorBmpTable`'s construction
(`Graphics.fs:850-945`) and its consumers (`OverworldMapTileCustomization.fs`),
composites a small 5×9 icon centered within the 16×11 tile (not a full-tile
image) from three sources: `ow_icons5x9.png` (14 icons) for sword caves,
secrets, door repair, money-making game, the letter, armos, hint shop,
take-any, and the potion shop; `icons3x7.png` (8 icons) for shops,
composited onto an orange background; and a painted digit on a colored
background (yellow for dungeons, orchid for any-roads) — no sprite at all.

## Acceptance criteria
- [x] `s_icon_overworld_strip39.png` removed from bundled resources;
      `ow_icons5x9.png` and `icons3x7.png` (the real sources) added, with
      `NOTICE.md`/`Package.swift` updated.
- [x] `OverworldTileMark.iconStripIndex` (a single flat 0...35 index into
      the wrong strip) replaced with `OverworldTileMark.iconSource`, an
      enum describing which real source (dungeon/any-road digit, one of 14
      `ow_icons5x9` sprites, one of 8 `icons3x7` shop sprites, or the
      whole-tile solid black for `.dontCare`) renders each mark — every
      index verified against the actual strip pixel content (contact
      sheets), not assumed from position/comments.
- [x] `OverworldMapView`'s `TileView` rewritten to composite the small
      interior icon at the correct position/size fraction within the tile
      (`x∈[5,10), y∈[1,10)` of a 16×11 tile, ported exactly from
      `Graphics.fs`'s `initFull()`), replacing the old full-tile icon
      overlay.
- [x] Tests rewritten: `OverworldInteriorIconAtlasTests`,
      `OverworldShopIconAtlasTests` (dimensions, valid/invalid indices,
      distinct content), and `OverworldTileMarkTests`'s `iconSource`
      completeness/uniqueness test covering all 36 marks against their real
      source index ranges. 85/85 total passing.
- [x] Manually verified against the running app: seeded all 36 marks
      (temporary, reverted before commit), screenshotted, and pixel-matched
      every rendered icon against direct crops of the real reference
      sprites — not just "it compiles and shows something."
- [x] `docs/domain.md` § 4.5/§ 6 and `docs/stack.md` updated with the
      correction, explaining what was wrong and why, not silently fixed.

## Out of scope
- The "darkened once obtained" variant — depends on the item/dungeon state
  layer (`T-013`/`T-014`), not yet built. Every icon currently renders its
  "available" variant.
- Two-item shop display (`makeTwoItemShopBmp` in the reference) — the
  current `OverworldTileMark.shop(ShopKind)` model only carries one item;
  extending it is a separate, explicit follow-up if wanted.
- HDN mode's lettered dungeon variant (`T-016`).

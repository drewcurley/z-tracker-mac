# T-045 — Preload the audio stack at launch (non-blocking)

## Description
The first reminder clip has a long cold-start delay: the first `AVAudioPlayer`
playback has to acquire the audio hardware (coreaudiod), and on some machines
that spin-up takes many seconds. Because `play()` runs on the main actor, the
acquisition also hangs the UI (beach ball) on the first play. The user
confirmed that once the stack is warm, clips fire instantly.

Two changes:
1. **Preload at launch** — warm the audio stack once when the app starts
   (on the startup screen, before any reminder), so the first real clip skips
   the cold-start cost.
2. **Non-blocking** — do the warm-up on a background task so acquiring the
   audio hardware never blocks the main thread / hangs the UI.

## Acceptance criteria
- [x] Audio stack is primed once at launch via `ReminderAudioPlayer.primeAudioStack()`
      from the root view's `.task`.
- [x] Warm-up runs off the main thread (`Task.detached`), at zero volume, so it
      is inaudible and never hangs the UI.
- [x] The warm-up clip resolves from the bundle (guarded by a test so it can't
      silently no-op if resources move).
- [x] No change to the real playback path; the first reminder benefits from the
      warm stack.
- [x] App launches cleanly (on-device); user to confirm the first-play lag /
      beach ball is gone on their (wedged-coreaudiod) machine.

## Notes
- The warm-up player is created and used entirely inside the detached task, so
  it needs no `Sendable` handling; it's released once done, having engaged the
  process's shared audio stack (which then stays warm for the session).
- Could not reproduce the multi-second coreaudiod hang on the build machine
  (audio device healthy there); the fix is validated architecturally + by the
  user's environment.

# T-190 — Start screen on always-empty screens

## Bug/ask
A run's start screen sometimes lands on an "always-empty" (dead-spot) overworld screen,
but those tiles were non-interactive, so you couldn't designate one as the start spot.

## Fix (OverworldMapView only)
- Dead-spot tiles stay hit-testable (dropped the `allowsHitTesting(!isAlwaysEmpty)` gate).
- They can't hold a mark: left-click still no-ops on them, and their right-click menu is a
  minimal **start-spot / waypoint** menu (`TileChooserModifiers.isDeadSpot` →
  `startSpotMenuItems`), not the mark chooser or enemy picker — in both menu and graphical
  modes.
- The violet start-spot ring already rendered independent of `isAlwaysEmpty`, so it shows
  once set; clearing works via the same menu.

## Notes
Voice `.setStart` already set the spot at the model level regardless of the tile, so this is
a UI-only gap. 722 tests pass (no logic change; the feature is view wiring, QA'd on-device).

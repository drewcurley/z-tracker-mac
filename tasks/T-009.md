# T-009 — Overworld routing: static adjacency graph

## Description
GYR highlighting and routing lines (`docs/domain.md` § 4.5) turned out to be
byproducts of a full graph-based pathfinding subsystem
(`Zelda1RandoTools/Z1R_Tracker/Z1R_Tracker/OverworldRouting.fs`), not a
simple feature — confirmed by reading the entire 468-line file. It models
the overworld as ~130 hand-specified adjacency edges (most screens are one
vertex, ~12 are split into two half-screen vertices for narrow passages),
with asymmetric Lost Woods/Lost Hills traps, ladder/raft-conditional
crossings, and a priority-queue multi-path breadth-first search on top.

Given the size, this is split into a foundation task (the static graph data
structure, faithfully transcribed and self-validated) before the dynamic
layer (screen-scroll variants, recorder-warp/any-road edges) and the actual
pathfinding search + GYR/route-line UI, which land as follow-ups.

## Acceptance criteria
- [x] `OverworldScreenPortion` (full/north/south/east/west) and `OverworldVertex`
      (x, y, portion) ported to `TrackerCore`, matching
      `OverworldRouting.fs:16-24` exactly.
- [x] The static adjacency graph (`populateStaticOverworldData`,
      `OverworldRouting.fs:26-209`) ported edge-for-edge: the grid-adjacency
      edges, the ~12 half-screen special cases, the Lost Woods/Lost Hills
      asymmetric traps, and the ladder/raft-conditional edges. **Verified
      by call-count comparison against the source**, not just visual
      transcription — every count (95 grid calls, 51 total `symmetricAdd`
      calls, 7 raw asymmetric calls) matched exactly between the F# source
      and the Swift port.
- [x] The reference code's own sanity check ported as a real test
      (`OverworldRoutingGraph.screenTypes`): every one of the 16×8=128
      screens resolves to a consistent screen type with `raft=true`
      (matching the reference comment that this only fully resolves with
      raft present) — mirrors `generateScreenTypeListImpl`'s own
      `failwith "mismatch"`/`failwith "bad map data"` guards, returning
      `nil` instead of crashing (this is reachable from live tracker state).
- [x] Additional tests: symmetry of `symmetricAdd`-derived edges, presence
      of the known asymmetric edges (Lost Woods/Lost Hills) in only one
      direction with the documented cost asymmetry (2 forward / 8 backward),
      ladder/raft conditional edges present only when the item is held.
- [x] Not wired into any UI — this is the data-layer foundation only, as scoped.

## Out of scope (tracked as follow-ups)
- Screen-scroll variants (mirrored/normal overworld), recorder-warp and
  any-road dynamic edges (`populateDynamic`).
- The actual pathfinding search (`findAllBestPaths`) and GYR/route-line UI.
- Wiring routing into the live tracker state (current ladder/raft
  possession, marked any-roads, etc.).

## Risks / dependencies
- Depends on `T-008` — complete.
- **High transcription-error risk**, called out explicitly: ~130 hand-coded
  coordinate edges is exactly the kind of data a single typo can silently
  corrupt. Mitigated by porting the reference code's own sanity check as a
  real test (not inventing a new one) and by keeping this task scoped to
  the graph alone, reviewable independently of any UI.

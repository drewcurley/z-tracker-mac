# T-011 — Overworld routing: hover-based route lines + reachability highlight

## Description
`T-009`/`T-010` ported the full routing algorithm (static graph, dynamic
layer, `findAllBestPaths`) as pure, tested data/algorithm code, deliberately
not wired into any UI. Reading the reference app's UI half in full
(`Z1R_WPF/OverworldRouteDrawing.fs`, `Z1R_Avalonia/OverworldRouteDrawing.fs`)
surfaced that full GYR (green/yellow/red) coloring depends on a large
item-possession + dungeon-progress state layer (`TrackerModel.fs`'s
`MapStateSummary`/`recomputeMapStateSummary`, `playerComputedStateSummary`,
per-dungeon completion/triforce tracking, sword-cave/armos progress) that
`z-tracker-mac` has not built at all yet — a separate, substantial feature
area, not routing-UI wiring.

**Scope decision (developer, 2026-07-02):** ship a minimal slice now rather
than block on that state layer or build it inline. This task delivers real,
correct route-line rendering and a *reachability* highlight (nearest
unmarked, reachable tiles from the hovered screen) using only state that
already exists (tile marks). It explicitly does **not** attempt true GYR's
red ("inaccessible")/yellow ("sometimes empty") distinctions, the
destination-picker menu, or live item-possession wiring — those move to
`T-012`, seeded below. This is a deliberate phased delivery, not tech debt:
what ships is real and correct for what it computes, and the gap is
documented, not silently faked.

## Acceptance criteria
- [x] Pure `TrackerCore` computation (`OverworldRoutingGraph.routeHighlight`):
      given a hovered vertex and the set of currently-unmarked tiles, use
      `findAllBestPaths` (goal = the non-existent sentinel vertex, matching
      the reference's "map all reachable locations" trick) to rank unmarked
      tiles by cost, bold-highlight the nearest N, pale-highlight the next
      M — ported structurally from `drawPathsImpl`'s highlight-selection
      loop, with tie-at-cutoff extension preserved.
- [x] Route-line predecessor-chain data ported from the same function.
      **Scope note:** since this task always calls `dynamicGraph` with empty
      `recorderWarpDestinations`/`anyRoads` (no live state to source them
      from — see below), no warp edges exist in the graph at all, so the
      reference's solid/dashed/skip line-style branching is unreachable in
      this slice and was correctly not ported as dead code — a comment in
      `OverworldRouteHighlight.swift` documents this and points to `T-012`,
      where real warp destinations reinstate the distinction. Every line in
      this task is a solid, cost-faded walk, which is what the algorithm
      actually produces given the current inputs.
- [x] Rendered on `OverworldMapView` (`OverworldRouteLinesOverlay`) using
      coordinates computed relative to each tile's actual on-screen frame
      (`GeometryReader`/`tileWidth`/`tileHeight`), not the reference's
      fixed-pixel `Canvas` — verified by resizing the running app's window
      and confirming lines/highlights stayed correctly aligned at multiple
      sizes, not just at the default.
- [x] `ladder`/`raft`/`isMirror` are documented placeholder constants in
      `OverworldMapView` (`true`/`true`/`false`) — no item-possession or
      mirror-overworld state exists yet to wire to instead (`docs/domain.md`
      § 6, `tasks/T-012.md`). `canScreenScroll` turned out to have real state
      already (`TrackerOptions.showScreenScrolls`, ported in T-004/T-005),
      so that one *is* wired live, better than the plan assumed.
- [x] Tests: 5 deterministic, hand-verified tests in
      `OverworldRouteHighlightTests.swift` — bold/pale selection with exact
      expected line segments and costs, tie-at-cutoff extension, zero-budget
      (no highlights but lines still computed), empty-destination-set, and
      an unresolvable-destination-is-skipped-not-crashed case.

## Manual verification
Ran the built app, clicked through to the main tracker view, and used
synthesized mouse-move events (`CGEvent`) to hover the live overworld map:
confirmed route lines fan out from the hovered screen with cost-based
fading, unmarked screens get bold/pale green highlights, and re-verified
after resizing the window to two smaller sizes that the lines/highlights
stayed correctly aligned to the actual (changed) tile positions — the
responsive-coordinate requirement holds, not just in theory.

## Out of scope (tracked as `T-012`)
- True GYR: red (inaccessible)/yellow (sometimes-empty) distinctions —
  require `OwGettableLocations`/`SometimesEmpty` equivalents, which require
  the item/dungeon state layer.
- The destination-picker menu (specific tile, shop type, dungeon, WS/MS
  cave, remaining open caves).
- Wiring `dynamicGraph`'s `ladder`/`raft`/`isMirror`/`canScreenScroll` to
  live state (requires the item-possession/mirror-overworld state layer).
- The take-any pie-menu accelerator and hover magnifier — unrelated
  reference-app features, not part of routing.

## Risks / dependencies
- Depends on `T-010` — complete.
- The responsive-coordinate rendering (vs. the reference's fixed canvas) is
  new ground for this app — no prior task has drawn cross-tile overlay
  geometry on the reflowing grid yet.

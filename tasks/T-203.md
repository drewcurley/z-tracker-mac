# T-203 — Real fix for the Sequoia launch crash

## Why T-202 wasn't enough
Adding an `Info.plist` to the resource bundle (T-202) did **not** fix the macOS 15 crash — the
tester's v0.8.2 report showed the identical trap: `Bundle.module`'s lazy static initializer
running `fatalError("unable to find bundle")` on the first icon load
(`GameSprite.image` → `ItemGlyph`). The problem is `Bundle.module`/`Bundle(url:)` itself
rejecting the nested SwiftPM resource bundle on Sequoia — not the plist.

## Fix
Stop depending on `Bundle.module` entirely. New `AppResources.url(forResource:withExtension:)`
resolves resource files by **direct file path** (composed from `Bundle.main.resourceURL` /
`Bundle(for:)` URL properties + `FileManager.fileExists`), never calling `Bundle(url:)` on the
nested bundle. All 7 `Bundle.module.url(...)` call sites (GameSprite, FauxItemsHUD,
ItemIconAtlas, the overworld/heart atlases) now use it, so **nothing references `Bundle.module`
anymore** — its `fatalError` initializer never runs. The search roots cover both the `.app`
(`Contents/Resources/<bundle>`) and the test runner (bundle beside the `.xctest`).

The T-202 Info.plist is left in place (harmless; the bundle is no longer loaded as a `Bundle`).

## Tests
`AppResourcesTests`: known GIF + PNG atlases resolve to real files; a missing resource returns
nil (no trap). 732 tests pass. x86_64 build QA'd under Rosetta (user: "it seemed to work").
`VERSION` → 0.8.3.

## Note
This is bulletproof by construction: a plain existence check on a composed path can't hit the
bundle-validation code that Sequoia rejects. Final Sequoia launch confirmation is the tester's.

# T-228 — Responsive low-resolution layout

Improvements for players on a **single 1080p monitor** running the game and the tracker side by
side. The tracker adapts as the window narrows so the important data (dungeon items, item tracker,
maps) stays visible without the Flags/Info panels wrapping down and pushing everything below the
fold. Ships (with [T-229](./T-229.md)) as **v1.2.7**.

## Behavior
- **Auto dungeon-map scale.** The dungeon room-map auto-scales as the band narrows: **100%** normally,
  **80%** at ≤ 975 wide, **60%** at ≤ 850. Applied only when crossing a band, so a manual zoom is
  still respected between crossings.
- **"Show Flags panel" setting** (welcome screen + in-app settings), mirroring the existing "Show
  Info panel" toggle.
- **Auto-collapsing Flags/Info panels.** Rather than wrap below the trackers when the window is
  narrow, each panel collapses to a slim tap-to-expand chip: **Info collapses at ≤ 1035** (its wrap
  point), **Flags at ≤ 900**. The chips take almost no vertical/horizontal space; expanding is a
  temporary reveal. Rationale: there's no case where the Flags/Info panels wrapping omnipresent below
  the item trackers is useful.
- **Compact buttons on narrow windows.** Below **1100 wide**, the Dungeon-items and general-Items
  tracker buttons shrink 34 → 30px, and the Blockers boxes shrink 30 → 26px, to buy room and prevent
  wrapping.

## Acceptance criteria
- [x] Given a window ≤ 975 wide, the dungeon map is at 80% (≤ 850 → 60%); above 975 it returns to 100%.
- [x] Given the "Show Flags panel" setting is off, the Flags panel is hidden (welcome + in-app parity
      with "Show Info panel").
- [x] Given the window is ≤ 1035 wide, the Info panel is a collapsed chip; ≤ 900, Flags is too; each
      chip expands/collapses on tap without pushing the maps far down.
- [x] Given the window is ≤ 1100 wide, the tracker buttons render at 30px and the Blockers boxes at 26px.
- [x] The broadcast/mirror window is unaffected (renders full-size for streaming).

## Implementation
- `MainTrackerPlaceholderView` — central orchestration: a viewport-width reader on the **ScrollView**
  (not the content, whose wide children pin the min width) drives breakpoints; `collapsibleSection`
  renders either a `TopSectionGroup` or a slim chip + temporary content.
- `TrackerCompactKey` / `\.trackerCompact` environment Bool set once on the whole content; each view
  derives its own baseline (buttons 34/30 in `ObtainableItemsView`/`SeedFlagsView`/`MapInfoView`/
  `DungeonTrackerView`, blockers 30/26 in `BlockersView`).
- `DungeonBandView.autoMapScale(for:)` — the 100/80/60 band scale, applied on band crossings.
- `TrackerOptions.showFlagsPanel` — new persisted bool mirroring `showInfoPanel`;
  `SettingsPanelView` gains the "Show Flags panel" toggle.

## Out of scope
- Reflowing content *within* the zoom (that's the responsive breakpoints' job) — see [T-229](./T-229.md).
- Fitting the timeline on a 1080p screen — the tracker can still exceed 1080px tall; the timeline is
  an FYI, accepted by the user.

## Notes
- Width-measurement gotcha: measuring the content's `.background` yields the content **min** width
  (pinned by wide children), never dropping below ~760; the reader must sit on the **viewport**
  (ScrollView's own frame) to see true window width. This was the root cause of the chips not
  appearing in first QA.
- The env is a **Bool**, not an absolute size: blockers (30) and buttons (34) have different
  baselines, so a shared absolute size would wrongly resize blockers to 34.

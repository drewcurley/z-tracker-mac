# T-144 — Timer render CPU fix + FPS counter

## Description
The app sat at ~100% CPU (a pegged core) and lagged the game whenever the run
timer was going. **Diagnosed by live `sample`:** ~89% of CPU was in
`CA::Transaction::flush → NSHostingView.layout() → invalidateSizeConstraintsIfNecessary()
→ sizeThatFits`, i.e. the millisecond stopwatch's 33 fps `TimelineView` forced the
main window's single `NSHostingView` to re-measure the **entire** tracker view tree
(~68 ms/pass) every frame.

- **Fix:** the visible clock only needs `H:MM:SS`, so it now ticks **once per
  second** (`timerDisplayRefreshInterval = 1.0`) via `TimerFormatting.hms`. The
  millisecond value written to the notes (Zelda capture etc.) is unchanged — it's
  read from the timer at that instant via `hmsMillis`. Also: **no ticking while
  paused** (paused elapsed is constant, so it renders once, not 33×/sec).
  Measured **100% → ~13% CPU** with the timer running.
- **FPS counter (diagnostic, `TrackerOptions.showFPS`):** a small pill readout
  (Settings ▸ "Show FPS counter") driven by a `CADisplayLink` on the main run
  loop, so it reflects real main-thread frame delivery (drops during a stall).
  For measuring the remaining perf work.

## Acceptance criteria
- [x] Timer-running CPU drops from ~100% to ~13% (verified by `sample`).
- [x] Visible clock shows H:MM:SS, ticks 1 fps; capture-to-notes keeps ms.
- [x] No redraws while paused. FPS toggle persists. 588 tests pass.

## Known follow-ups
- Residual ~13% + the mousing jank share a root cause: on macOS 27 any layout
  invalidation re-measures the whole tree. Deeper fix (isolate hosting context /
  NSHostingView sizingOptions / slim per-tile bodies) → near-0%. Dungeon map hover
  is ~10× worse than overworld (separate task).

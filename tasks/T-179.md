# T-179 — Dungeon-hover FPS fix + file-based render-perf logging

## Description
Mousing over the dungeon room-map grid dropped to ~4–8 fps — roughly 2× worse than the
overworld. Diagnosed with purpose-built render-path instrumentation (rather than guessing),
then fixed the confirmed root cause. The instrumentation ships gated behind a Settings
toggle so it can be reused for future frame-rate work.

### Root cause + fix
- **`ViewThatFits` re-render (the culprit).** `DungeonBandView` chose side-by-side vs
  stacked with `ViewThatFits(in: .horizontal)`, which re-measures **both** candidate
  layouts — each embedding the full map **and** the blockers/notes column — on every
  subtree invalidation, i.e. 2–3× per cursor hover. Instrumentation confirmed dungeon
  hovers spent ~62–96 ms re-rendering the whole band (incl. `BlockersView`, 27×
  `BlockerBoxView`, `NotesView`) each move.
- **Fix:** replace `ViewThatFits` with a cached-width boolean (`useSideBySide`) driven by a
  `GeometryReader` width read, so the layout decision recomputes only on **resize**, not on
  hover. Confirmed: dungeon hovers dropped to ~15–26 ms and the blockers/notes column no
  longer re-renders per hover.
- **Layout-regression follow-up (same task).** The first cut of the width read routed
  through a `PreferenceKey` and delivered a stuck **0** (the reader was attached to a
  `.fixedSize` node that reports a 0-width frame to its own `.background`), so the band was
  permanently stacked regardless of window width. Fixed by reading the width **directly**
  off the `GeometryReader` proxy (`onAppear`/`onChange`) — the same pattern `ScaledFootprint`
  already uses — and ignoring degenerate 0-width passes.

### Render-perf logging tool (`PerfLog`)
- A Settings → Other toggle, **"Log render perf to file"**. When on: per hover, logs the
  hover event, every instrumented view body that re-evaluated (with SwiftUI's own reason via
  `Self._printChanges()`), and how long the main thread stayed busy afterward. Zero overhead
  when off.
- **File capture (Finder-launchable).** While enabled, the process's stdout+stderr are
  redirected to a temp file via `dup2`, so the capture includes `_printChanges` output (which
  writes straight to the console and can't be intercepted per line). Line-buffered so a
  near-hang still leaves the tail on disk. This is session-global — all console output lands
  in the file for the rest of the session.
- **Save on exit.** On **Reset App** or **Quit**, if a capture exists, prompt **Save… /
  Don't Save / Cancel** (NSSavePanel copy / delete temp / return to app). Chained after the
  save-run dialog on Quit; gated before Reset App. Reset App re-opens a fresh capture so a
  continuing session keeps logging.
- **Startup GC.** The temp-log folder is wiped once at launch (crash-safe cleanup).

### Also in this task
- **About build stamp.** `build-app.sh` bakes the git short hash (+ `-dirty`) and build time
  into `Info.plist` (`ZTrackerBuildStamp`), surfaced in About — so a running app can be
  confirmed to match the latest local build (used to rule out stale copies during diagnosis).
- Minor render-path hygiene surfaced while profiling: guarded `@Observable` writes and
  cursor-ring isolation in `TrackerFocusState` / `DungeonRoomGridView` (no redundant writes;
  the dungeon cursor ring re-renders independently of the grid).

## Acceptance criteria
- [x] Dungeon-hover cost cut from ~62–96 ms/hover to ~15–26 ms (instrumentation-confirmed);
      blockers/notes no longer re-render on hover.
- [x] Side-by-side ↔ stacked layout tracks window width again (regression from the fix fixed).
- [x] `PerfLog` toggle captures to a file, openable from Finder (no terminal), with the full
      `_printChanges` fidelity.
- [x] Reset App / Quit prompt to save-or-discard the capture; Cancel returns to the app.
- [x] Leftover logs auto-cleared at launch.
- [x] Zero overhead when the toggle is off; all 687 tests pass.

## Notes
- The `ViewThatFits` removal is the FPS win; earlier micro-fixes (guarded writes, cursor-ring
  isolation) helped the overworld path but were **not** what fixed the dungeon stall — kept
  as reasonable hygiene, not credited as the fix.
- Trade-off accepted (user): the file capture redirects the whole session's console (the price
  of capturing `_printChanges`) and is one-way for the session; moot when launched from Finder.

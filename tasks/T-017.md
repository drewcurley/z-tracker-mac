# T-017 — Dungeon blockers

## Description
A player-annotation system layered on top of, but distinct from, item
possession: the player marks *why* they got stuck in a dungeon (missing
bow/arrow, ladder, key, bait, money, bomb, or a combat blocker), and the
tracker helps decide when that annotation is stale (item since acquired)
and reminds the player they can go back. Grounded in
`TrackerModel.fs:1147-1273` (~127 lines):

- `DungeonBlocker` union (`:1147-1248`, ~16 cases: real + "MAYBE_" variants
  of BOW_AND_ARROW/RECORDER/LADDER/KEY/BAIT/MONEY/BOMB, plus COMBAT and
  NOTHING).
- `CombatUnblockerDetail` (`:1250-1253`: BETTER_SWORD/BETTER_ARMOR/WAND).
- `DungeonBlockerAppliesTo` (`:1254-1256`: 6-bool array — which UI element
  the annotation attaches to).
- `DungeonBlockersContainer` (`:1257-1273`, ~17 lines: static 8×3 grid of
  blockers-per-dungeon + applies-to grid, with `AsJsonString` for save/load).
- `PlayerCouldBeBlockedByThis()` (`:1188-1194`) — reads
  `playerComputedStateSummary.{HaveLadder,HaveRecorder,HaveBow,ArrowLevel,
  HaveAnyKey}` (from `T-014`) to decide staleness.

Self-contained: reads player-state but doesn't feed back into it, so it's
cleanly separable and deferrable relative to the core item/dungeon model.

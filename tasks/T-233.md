# T-233 — AppResources must handle the deep resource-bundle layout

## Problem
After the 2026 Xcode/toolchain update (same one that forced re-accepting the Xcode license this
session), the whole `ZTrackerMacTests` image suite went red — `OverworldBackgroundAtlas`,
`OverworldInteriorIconAtlas`, `OverworldShopIconAtlas`, `AppResources` — every atlas returning nil.
It reproduces on clean `main`, so it's purely environmental.

**Root cause (not a decode failure — a lookup failure):** the update changed the nested SwiftPM
resource bundle from a **flat** folder (`…/ZTrackerMac_ZTrackerMac.bundle/<file>`) to a proper
**deep** macOS bundle (`…/ZTrackerMac_ZTrackerMac.bundle/Contents/Resources/<file>`). `AppResources`
— the deliberate direct-path loader that avoids `Bundle.module` (T-203, which trapped on Sequoia) —
only composed the *flat* path, so every probe missed and `AppResources.url(...)` returned nil. Both
CoreGraphics decode paths were verified working standalone, ruling out an image-decode regression.

**Severity beyond tests:** `AppResources` is the app's runtime sprite/atlas loader too. The built
`.app` currently still uses the flat layout (so the app works today), but the same toolchain change
that moved the *test* bundle deep could move the app bundle deep on a clean rebuild — which would
silently break **every sprite in a shipped release**. Probing both layouts is durable insurance.

## Fix
In `AppResources.searchRoots`, for each nested candidate probe **both**
`…/<bundle>` (flat, old toolchains) and `…/<bundle>/Contents/Resources` (deep, new toolchains).
Still pure `FileManager.fileExists` on composed paths — no `Bundle(url:)`/`Bundle.module`
validation (preserving the T-203 design intent).

- [x] Still works on the flat layout (older toolchains / the current `.app`) — both paths probed.

## Out of scope
- No app-behavior change (the app already loaded resources on the flat layout); this restores the
  test gate and future-proofs the loader.

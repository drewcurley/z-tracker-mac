# T-232 — TAG must require a reachable level 9

## Problem (from a real run)
A player held all 8 triforces plus the go-items (bow, silver arrows, ladder), but **level 9's
entrance sat under a power-bracelet overworld spot** and the power bracelet was still inside a
dungeon they hadn't finished looting. Every remaining overworld spot was ungettable, so they
**could not actually reach level 9** — yet the tracker kept announcing "You are Triforce and Go."

Root cause: `TriforceAndGoSummary.compute` gates full TAG on
`missingDungeonCount == 0 || unreachableCount == 0`. There is a guard
(`unreachablePossibleDungeonSpotCount`) meant to catch exactly this, but it's **OR-ed** with
`missingDungeonCount == 0`; once all eight *numbered* dungeons are located, that term is true and
the unreachable guard no longer matters — even though level 9 itself is still walled off.

## Fix
Add a reachability gate: level 9 must be **located**, or **at least one overworld spot must be
gettable** (some spot you can still uncover, which might be 9). Otherwise it isn't TAG. This is
conservative — it only bites when 9 is unlocated **and** nothing at all is gettable (the true
dead-end) — and falls through to the existing heuristic score, whose sub-101 text
("You need something to be triforce and go") is the honest "not yet" note. Scope per the user:
**suppress the false TAG only** — no item-naming or dependency-chain hints.

```swift
let level9Located = mapState.dungeonLocations[8] != nil
let canReachLevel9 = level9Located || mapState.owGettableLocations.trueCount > 0
if canReachLevel9 && (missingDungeonCount == 0 || unreachableCount == 0) { … TAG … }
```

## Acceptance criteria
- [x] Given full TAG items + all triforces, but level 9 unlocated and zero gettable overworld spots,
      the summary level is **< 101** (no false TAG).
- [x] Given level 9 **is** located, full TAG still reports 103 even if nothing else is gettable
      (no over-suppression).
- [x] All pre-existing TAG scoring (103/102/101/score) is unchanged in every other case.

## Out of scope
- Naming the blocking item(s) or "it's in level N" hints, and the transitive bracelet→raft→9 chain
  (the tracker generally can't know what item sits at an arbitrary overworld spot). Considered and
  declined for this pass; could be a future enhancement.
- The "level 9 is *marked* but its entrance is item-blocked" case (blocker computation for located
  dungeons doesn't exist yet); the user's dead-end was the unlocated case.

## Notes
- `haveRecorder` in TAG is deliberately mirrored from `haveLadder` (preserved upstream bug); this
  fix does not touch that.
- Discovered in passing: the **ZTrackerMacTests image/atlas tests fail in this environment** (they

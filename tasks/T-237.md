# T-237 — Mid-run quest switch

## Why
If you start a run having picked the wrong overworld quest (e.g. "First" when the ROM is really
"Mixed — First"), there was no way to fix it without restarting. The data model already recomputes
everything quest-derived (background art, terrain masks, spot totals, mixed-quest dimming) from
`model.quest` live, so switching mid-run is cheap and leaves marks intact.

## Behavior
- A new **"Overworld quest"** picker at the top of the in-run **Settings** window (shown only once a
  quest is chosen — the startup screen has its own picker).
- Choosing a different quest shows a **confirmation dialog** noting it re-derives valid spots and may
  affect existing markings. On confirm, the quest swaps and everything re-derives live; marks are kept.

## Implementation
- `TrackerModel.changeQuest(_:)` — swaps `quest` only; unlike `selectQuest` it does **not** re-seed
  dungeon floor-item hearts (a once-at-start step that would clobber in-run edits).
- `OverworldQuest.displayName` — shared label (startup + the new picker).
- `SettingsWindowView` gains `model` and hosts the picker + confirmation; `ZTrackerMacApp` passes
  `model` to the Settings window.

## Acceptance criteria
- [x] Mid-run Settings shows the quest picker; picking a different quest confirms first.
- [x] On confirm, `model.quest` changes and overworld marks are untouched.
- [x] First ↔ Mixed-First switch is non-destructive (shared 73 total; mixed is a superset of valid spots).

## Notes
- `quest` already persists in the save, so a mid-run change rides along. The confirmation is kept even
  for the safe first/mixed-first case (per the user) as a general guard; far-apart switches
  (e.g. first ↔ second) genuinely change the valid-spot set and distribution.

# T-069 — Revisit live TTS now that the audio stack is pre-warmed

## Description
**User observation (2026-07-15):** on the **startup screen**, switching voice
models under "Change voice…" previews the voices and they play back **instantly**
— no spin-up lag. That screen still uses live `AVSpeechSynthesizer` (it was never
migrated to pre-rendered clips like the main app was in T-024). If live TTS is now
instant, the original reason for the pre-rendered clips may be gone.

Context: T-024 switched reminder voice to **pre-rendered `m4a` clips** because the
first `AVSpeechSynthesizer.speak` cold-started the speech service and lagged the
first spoken reminder ~20s. Since then, **T-045 pre-warms the process audio stack
(coreaudiod)** at launch. The open question: does warming the audio output stack
*also* resolve the speech-synth first-use lag, or did switching to clips mask a
separate `AVSpeechSynthesizer` warm-up cost that the startup screen happens to pay
earlier?

If live TTS is reliably instant, we could **return to generated speech** and use
the **Zoe premium** voice — removing the pre-render pipeline
(`scripts/generate-reminder-audio.sh`), the bundled `Resources/audio/*.m4a`, and
the clip/TTS branching in `ReminderController.handle`, and gaining fully dynamic
text (any announcement, not just the pre-rendered set).

## Investigation to do first (don't assume)
- Confirm whether the startup screen's instant preview is because the synth was
  already warmed by that point, or a genuinely different/cheaper path.
- Measure first-`speak` latency in the **main app** with T-045's warm-up in place
  (cold launch → first reminder), with and without an explicit `AVSpeechSynthesizer`
  warm-up (speak an empty/zero-volume utterance at launch, à la T-045).
- Verify the **Zoe premium** voice is present by identifier and falls back
  gracefully if the user hasn't downloaded it.
- Weigh the tradeoff: clips are deterministic and instant but fixed-text and add
  bundle weight + a generation script; live TTS is dynamic but depends on the
  installed voice and warm-up behaving.

## Acceptance criteria (draft)
- [ ] Documented measurement of first-`speak` latency in the main app with the
      current warm-up (pass/fail against an instant-enough bar, e.g. < ~300ms).
- [ ] Decision recorded: keep clips, move to live TTS, or hybrid.
- [ ] If moving to TTS: Zoe-premium selection + graceful fallback; dead clip
      pipeline/assets removed; reminders still honor volume + per-category toggles;
      serialized via T-068's queue.

## Notes
Pairs with T-068 (serialization applies either way). If we keep clips, at least
fix the startup screen's voice preview to share the same warm-up so it's honest
about what the main app does.

## Resolution (2026-07-16)
Moved to **live TTS**. One shared `SpeechEngine.AVSpeechSynthesizer` speaks all
reminders with the **Zoe (Premium)** voice (graceful fallback to the system voice
if absent), primed at launch by speaking a silent space so the first reminder is
instant. Removed the whole clip pipeline: `ReminderAudioPlayer`, the 40 bundled
`Resources/audio/*.m4a`, `scripts/generate-reminder-audio.{sh,swift}`, the
`ReminderAnnouncement.audioKey` property, and the clip/TTS branch in
`ReminderController`. Reminders are now any-text and dynamic. Latency on a cold
launch needs the user's real-run confirmation (can't be measured headlessly).

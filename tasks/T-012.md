# T-012 — Player state layer + full GYR routing

## Description
`T-011` shipped a minimal routing slice (route lines + a simple
"reachable/unmarked" highlight) using only state that already exists in
`z-tracker-mac` (tile marks). The reference app's real "Link" feature goes
further: true GYR coloring (green/yellow/red — accessible, sometimes-empty,
inaccessible) and a destination-picker menu, both of which depend on a large
item-possession + dungeon-progress state layer that hasn't been ported at
all yet:

- `TrackerModel.fs`'s `MapStateSummary`/`recomputeMapStateSummary`
  (`TrackerModel.fs:1013-1139`) — dungeon completion per dungeon, triforce
  count, sword-cave progress (magic/white sword thresholds), armos box
  state, shop-discovery flags, "gettable location" and "routeworthy" spot
  classification.
- `playerComputedStateSummary` — item possession (ladder, raft, recorder,
  power bracelet, bombs, candle level, etc.) and derived flags
  (`HaveLadder`, `HaveRaft`, `HaveCoastItem`, etc.) consumed throughout
  `recomputeMapStateSummary` and `OverworldRouteDrawing.fs`.
- Per-dungeon tracker state (`GetDungeon(x).IsComplete`,
  `.PlayerHasTriforce()`) — not yet characterized in depth for this project;
  read the relevant dungeon-tracker source in full before scoping further
  (this task's own first subtask).

This is a genuinely large, mostly self-contained feature area (the "item
tracker" / "dungeon tracker" backbone), not incidental to routing — it likely
needs its own foundation-then-consumers split, the same shape `T-009`/`T-010`
used for the routing algorithm itself. **Scope the split as this task's first
step**, don't assume the two-piece breakdown below is final.

## Acceptance criteria (indicative — refine after scoping)
- [ ] Item-possession state ported to `TrackerCore` (ladder, raft, recorder,
      power bracelet, bombs, candle level, sword level, etc.), grounded in
      `playerComputedStateSummary`.
- [ ] Dungeon-progress state ported (completion, triforce, per-dungeon item
      locations as needed for gettable-location logic).
- [ ] `MapStateSummary`-equivalent recomputation ported, producing
      "gettable"/"routeworthy"/"sometimes empty" classifications matching
      the reference exactly.
- [ ] `T-011`'s routing UI upgraded from the "reachable/unmarked" stand-in
      highlight to true GYR (red/yellow/green), and `dynamicGraph`'s
      `ladder`/`raft`/`isMirror`/`canScreenScroll` wired to this new live
      state instead of the placeholder `true`/`false` constants.
- [ ] Destination-picker menu (specific tile, shop type, dungeon, WS/MS
      cave, remaining open caves), matching the reference app's own
      taxonomy.
- [ ] Tests at every layer — this is exactly the kind of large hand-ported
      state machine where the call-count-comparison discipline (`T-009`)
      and known-scenario regression tests (`T-010`) both apply.

## Out of scope
- The take-any pie-menu accelerator and hover magnifier.

## Risks / dependencies
- Depends on `T-011` — complete (minimal routing slice must exist to have
  something to upgrade).
- **Largest single feature area scoped so far** — likely needs its own
  multi-task breakdown before implementation starts, not a single PR.

# T-012 — Player state: starting items + progress flags (foundation)

## Description
`T-011` shipped a minimal routing slice using only state that already
exists in `z-tracker-mac` (tile marks), deferring true GYR coloring and the
destination-picker menu to a full item-possession + dungeon-progress state
layer. That layer turned out to be large enough to need its own
foundation-then-consumers breakdown, the same shape `T-009`/`T-010` used for
the routing algorithm — grounded by reading `TrackerModel.fs` (1878 lines)
in full. **This task is the foundation piece; `T-013` through `T-018` are
the seeded follow-ons** (see `docs/domain.md` § 6 for the full staged plan
and why it's split this way).

This task ports the two smallest, fully self-contained, dependency-free
data bags identified in that read-through:
- **`StartingItemsAndExtras`** (`TrackerModel.fs:535-570`, ~36 lines) — seed-
  configured starting inventory: 8 HDN starting-triforce-piece bools, 15
  starting-item bools (`PlayerHasWhiteSword`, `PlayerHasMagicalSword`,
  `PlayerHasLadder`, `PlayerHasRaft`, `PlayerHasRecorder`, etc.), and
  `MaxHeartsDifferential : int`. Save/load shape: `SaveAndLoad.fs:108-151`.
- **`PlayerProgressAndTakeAnyHearts`** (`TrackerModel.fs:492-532`, ~41
  lines) — runtime-acquired progress not tied to a spatial dungeon-box
  location: `TakeAnyHearts : int[4]` (per-slot tri-state), and 9 progress
  bools (`PlayerHasWoodSword`, `PlayerHasMagicalSword`, `PlayerHasBombs`,
  `PlayerHasDefeatedGanon`, etc.). Save/load shape: `SaveAndLoad.fs:56-92`.

Both are plain, independently-portable data bags with no entanglement with
dungeon-box UI — they only ever feed *into* `PlayerComputedStateSummary`
(`T-014`), never the reverse. Porting them first, alone, gives `T-013`/
`T-014` real inputs to test against instead of hand-mocked stand-ins.

## Acceptance criteria
- [x] `StartingItemsAndExtras` ported to `TrackerCore` as an `@Observable`
      type, field-for-field against `TrackerModel.fs:535-570`, defaults
      verified against `SaveAndLoad.fs:108-151`'s load-time defaults (all
      `false`/`0`, confirmed — the save/load model never applies a
      non-default value on a fresh save).
- [x] `PlayerProgressAndTakeAnyHearts` ported likewise, against
      `TrackerModel.fs:492-532` / `SaveAndLoad.fs:56-92`. Modeled
      `TakeAnyHearts`' raw `int` tri-state as a proper `TakeAnyHeartState`
      enum (`.untaken`/`.takenHeart`/`.takenPotionOrCandle`) rather than a
      bare `Int`, with raw values pinned by test to the reference's 0/1/2.
- [x] Both owned by `TrackerModel` (`startingItemsAndExtras`,
      `playerProgress`) and surfaced via a bare-bones, explicitly-labeled
      "Player state (debug — T-012 foundation, not the real item tracker)"
      disclosure panel in `MainTrackerPlaceholderView` — manually verified
      against the running app (expanded the panel, toggled Ladder, screenshot
      confirmed the checkbox state actually flipped, not just a static mock).
- [x] Tests: 9 new tests across two suites — full default-field comparison
      for both types, independent-settability, explicit-initializer-values,
      `resetAll()` zeroing every field, and `TakeAnyHeartState` raw-value
      pinning. 81/81 total passing.

## Out of scope (tracked as follow-ons)

- `T-014` — `PlayerComputedStateSummary` derivation (depends on this task
  + `T-013`).
- `T-015` — Shop/cave-discovery additions to the overworld recompute, real
  GYR, destination picker, and wiring `T-011`'s placeholder
  `ladder`/`raft`/`isMirror` constants to live state.
- `T-016` — HDN (Hide Dungeon Numbers) mode's dungeon labeling/basement-
  stair-rendering metadata — a large orthogonal complexity multiplier,
  deferred until the DEFAULT-mode core is solid.

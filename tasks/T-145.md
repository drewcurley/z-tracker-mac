# T-145 — Dungeon popover consolidation

## Description
Right-clicking a dungeon room to open the detail picker had a ~500 ms delay and
the chooser intermittently crashed (NSPopover/ViewBridge, macOS 27). Root cause:
`RoomCellView` carried **three** `.popover` modifiers each with its own `@State`,
and it's instantiated once per room → **64 × 3 = 192 popover anchors** in the live
view tree, all carried through every layout pass.

- **Fix:** lift the picker state to the grid — one `@State activePicker:
  RoomPickerRequest?(col, row, kind)` and **3 grid-level popovers** (room type /
  monster / floor drop), each anchored to the active cell's exact rect (the grid
  is absolutely positioned with static `pitchX/pitchY`, so the rect is
  computable). Cells just call `onPick(kind)`. Result: **3 popovers, not 192.**
- Behaviour preserved exactly: right = room type, shift-left / scroll-up =
  monster (stays open to add a 2nd, T-116), shift-right / scroll-down = floor
  drop, arrow edge `.bottom`, VoiceOver named actions.
- Present via a `disablesAnimations` transaction (trims SwiftUI's own animation).

## QA (user, live)
- Popover anchors correctly at the clicked room; feels a bit snappier.
- The residual "expand" is the built-in **NSPopover** animation (AppKit-level;
  SwiftUI `.popover` doesn't expose a disable). Per the user's call, left as-is.

## Known follow-up
- Fully eliminating the animation **and** the crash means dropping NSPopover for a
  custom instant overlay card (deferred by user choice). See the popover-crash task.

- [x] Behaviour identical (room/monster/floor-drop, 2nd-monster stay-open). 588 tests.

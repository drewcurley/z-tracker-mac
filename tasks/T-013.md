# T-013 — Player state: Box/Dungeon core

## Description
The largest, most structurally interesting piece of the player-state
system, per the `T-012` scoping read-through — all in
`TrackerModel.fs:582-837` (~257 lines, 6 types):

- **`PlayerHas`** enum (`:582-585`) — `YES | NO | SKIPPED` tri-state.
- **`Box`** class (`:598-662`, ~65 lines) — one item slot (a `Cell` for
  "what's known to be there" + a `PlayerHas` tri-state + a change event).
  `IsDone()` (= cell known AND playerHas≠NO) is the core predicate consumed
  everywhere downstream. Three standalone singletons — `ladderBox`,
  `armosBox`, `sword2Box` (`:664-666`) — are just instances of this same
  class, not a distinct subsystem (confirmed by the scoping read-through;
  don't build a separate "Armos" special case).
- **`DungeonTrackerInstance`** (`:673-737`, ~65 lines) — owns the 9
  `Dungeon` objects, `AllBoxes()` (flattened list consumed by `T-014`),
  `AllBoxProgress` (a UI-progress-bar float, low priority).
- **`Dungeon`** class (`:739-818`, ~80 lines) — `GetDungeon(i)`'s return
  type. `playerHasTriforce`, `playerHasMap`/`PlayerCanSeeMapOfThisDungeon`,
  `Boxes`, and **`IsComplete`** (`:789-813`) — the DEFAULT-mode logic is
  `playerHasTriforce && all boxes IsDone()`; HDN-mode logic (2-vs-3-box
  quest-dependent completion) is explicitly **out of scope for this task**,
  see `T-016`.

**Explicitly deferred to `T-016`:** `StairKind`/`BoxOwner` enums
(`:587-597`) and `CurrentlyHasBasementStair` (`:607-632`) — these are
UI-rendering metadata (which dungeon-room-grid cell a box's stair icon
occupies) entangled with per-vanilla-dungeon-shape knowledge, not part of
the core possession/completion model. Likewise HDN-mode's
`Color`/`LabelChar` per-dungeon labeling (`:816-818`) and
`DungeonTrackerInstanceKind.HIDE_DUNGEON_NUMBERS`'s box-count/completion
variant.

## Acceptance criteria
- [ ] `PlayerHas`, `Box`, `Dungeon` (DEFAULT-mode only — 9 dungeons, 2-3
      boxes each per the reference's default box-count table), and enough
      of `DungeonTrackerInstance` to construct all 9 + the 3 standalone
      boxes and expose `AllBoxes()`.
- [ ] `Dungeon.IsComplete`, `.PlayerHasTriforce()`/`ToggleTriforce()`
      ported and tested against hand-constructed scenarios (all boxes
      done + triforce = complete; any box undone = not complete; etc.).
- [ ] `GetTriforceHaves()` (`:823-836`) ported — an 8-bool triforce-owned
      array, DEFAULT-mode indexing only.
- [ ] Tests: the call-count/field-count verification discipline from
      `T-009` applies again here (9 dungeons × correct box counts, matching
      the reference's default table exactly) plus scenario-based
      completion tests.

## Out of scope (tracked as follow-ons)
- HDN-mode dungeon count/completion variant, `Color`/`LabelChar`,
  `StairKind`/`BoxOwner`/`CurrentlyHasBasementStair` — `T-016`.
- `PlayerComputedStateSummary` derivation that consumes `AllBoxes()` —
  `T-014`.
- Dungeon blockers — `T-017`.

## Risks / dependencies
- Depends on `T-012` (`Cell`/`ChoiceDomain` primitives may already be
  reusable from the existing overworld-mark infrastructure — check before
  re-porting; the scoping read-through flagged this as likely-shared
  infra, not confirmed).
- Second-largest transcription-risk task so far after the routing graph —
  9 dungeons × 2-3 boxes is a lot of hand-specified structure to get
  exactly right; use the established call-count-comparison discipline.

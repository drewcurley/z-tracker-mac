# T-182 — Dungeon drag-to-swap item boxes

**State:** done (QA-approved — "behavior looks good")
**Branch:** feat/dungeon-drag-swap

## Why
The spoiler importer (T-181) fills each dungeon's boxes in the order the log lists
them, because the log doesn't distinguish a dungeon's **floor** item from its
**basement** item. It also can't recover from ordinary mis-marks. A direct
drag-to-swap gives the user a one-gesture correction.

## Scope
- Drag any dungeon item box onto **another box in the same dungeon** to exchange
  their contents (item id + taken/possession state).
- Cross-dungeon and named-box (coast/armos/white-sword) swaps are **out of scope**
  for v1 (matches the request: floor↔basement).
- Disabled boxes (an identified two-boxer's third slot) neither drag nor accept.

## Implementation
- `Box.swapContents(with:)` (TrackerCore) — exchanges cellCurrent + playerHas;
  no-op against itself. Swapping within one item set preserves item uniqueness,
  so it's always legal.
- `DungeonBoxRef` (`Transferable`, custom UTI `com.ztracker.dungeon-box`, declared
  in `UTExportedTypeDeclarations`) as the drag payload (dungeonId + boxIndex).
- `DungeonBoxSwapModifier` on each box in `DungeonCardView`: `.draggable` +
  `.dropDestination`, guarded to same-dungeon; green ring highlights the drop target.

## Tests
- `DungeonBoxTests`: swapContents exchanges both fields; swap-with-empty moves the
  item; swap-against-self is a no-op. (707 total pass.)

## QA checklist
- [ ] Drag floor item onto basement (and back) → contents swap, taken-state follows.
- [ ] Existing box interactions still work: **left-click toggles taken**,
      **right-click opens the picker**, hover cursor ring unaffected.
- [ ] Drag does not accept a drop from a different dungeon.
- [ ] Two-boxer third slot doesn't participate.

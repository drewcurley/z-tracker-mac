# T-214 — Gated-item acquisition defaults

The randomizer gates a few items behind requirements the tracker can't seed-snoop, so marking
them should default to **untaken** when the player provably can't have reached them yet.

## Behavior
- **Coast item** — needs the **ladder**. Without it, identifying the item defaults to untaken.
- **White Sword item** — needs a **4–6** heart-container minimum by seed → gate at **4**; below
  that, defaults to untaken.
- **Magical Sword** — needs **10–14** by seed → gate at **10**; below that, marking it held is
  **blocked** (it's a plain on/off toggle with no untaken state — user chose "block turning it on").

At or above each threshold, the user's left/right clicks are trusted as before (a seed with a
higher real requirement still lets you mark it). Coast/WSI remain *soft* defaults — the box can
still be toggled taken by hand, since a player may not track everything.

## Implementation
- `ItemAcquisitionGate` (TrackerCore) centralizes the thresholds + reachability from
  `PlayerComputedStateSummary` (`playerHearts` = max containers, from 3).
- `BoxItemPicker` / `BoxView` gain `defaultAcquired`; a left-click marks untaken when false. Wired
  at both entry points: the overworld item prompt (coast F16 / white-sword cave) and the Items-grid
  picker boxes.
- `ItemToggleBox` gains `canAcquire`; blocks turning the magical sword on below the gate. The
  overworld magical-sword cave click is gated the same way.

## Tests
`ItemAcquisitionGateTests` — the ladder gate + the 4/10 heart minimums. **753 tests pass.**

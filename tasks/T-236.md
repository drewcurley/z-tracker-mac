# T-236 — Voice item-box acquisition gate

## Problem
Setting the **white sword item by voice** marked it as *owned* even with only 3 hearts. The GUI
picker gates this (T-214): below the item's requirement — the white-sword item's heart minimum (4),
or the coast item's ladder — identifying the item marks it **"identified, not yet taken"** rather
than owned. The voice path bypassed that gate: `ItemBoxVoiceApply.apply` → `ItemBoxMark.apply` always
set `playerHas: .yes`.

## Fix
Thread the player state into the voice path so it uses the same `defaultAcquired` gate as the GUI:
- `ItemBoxMark.apply` gains an `acquired: PlayerHas = .yes` param (default preserves hotkey/left-click
  behavior).
- `ItemBoxVoiceApply.apply` takes `playerState` and sets `acquired = box.defaultAcquired(playerState)
  ? .yes : .no`.
- `VoiceController` passes `model.playerComputedStateSummary`.

So voice "white sword item …" at 3 hearts now records *what* the item is without claiming you have it
(exactly like the GUI's first click); at 4+ hearts it's owned. Coast follows the ladder gate; armos
is ungated.

## Acceptance criteria
- [x] Voice-set white sword item at <4 hearts → `cellCurrent` set, `playerHas == .no`.
- [x] At ≥4 hearts → `playerHas == .yes`.
- [x] Coast item follows the ladder gate; armos is always owned.
- [x] Hotkeys/left-click unchanged (default `.yes`).

## Out of scope
- The item **hotkey** path still claims `.yes` on a fresh mark (a deliberate older decision); not
  changed here since the report was voice-specific. Possible follow-up if hotkey parity is wanted.
